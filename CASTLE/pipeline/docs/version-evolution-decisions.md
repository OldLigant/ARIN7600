# 版本演进：已确认的边界与后续实施依据

决策日期：2026-09-19。更新核对：2026-09-20。跨版本 audio 导入和身份解耦仍未实现；内容回读核验已有独立工具，并用于 v5 发布验证，尚未整合成正式发布子命令。

用户选择先完善文档，待实际需要时再改代码。本文件收窄并修正 `release-process.md` 中 R-06/R-07/R-11/R-12/R-13/R-14 的早期设想；这些条目不是自动执行的任务清单。当前运行状态另见带时间戳的 `STATUS.md`，本文件不判断云端任务是否完成。

| 事项 | 当前决定 | 以后启动的条件 |
|---|---|---|
| 跨版本继承 | 记录“新 run 显式继承已完成 audio”，按需实现 | 确实需要使用新的 annotation 配置，且复用 audio 有明显价值 |
| 在线 / Batch 身份解耦 | 有价值，但先记录兼容方案 | 需要更新其中一条管线，同时避免另一条管线在新版下无谓失去检查点复用 |
| 内容哈希核验 | 只读核验、报告差异；不扩展为完整加固体系 | 下次需要检查发布内容时，先使用已有工具，再决定是否整理成正式命令 |

## 1. 保留现有部署方式

本地 Git 管理源码历史、tag 与 release manifest；`Ligant/castle-code/<release>` 保存每个版本的一套完整运行文件；HF Job 挂载指定目录。继续使用这种发布快照形式，不要求更换 bucket、引入新存储系统或让 worker 从 Git 拉代码。

每条 run 固定一个代码身份和请求配置。v3/v4/v5 是已有的兼容关系：三个 release 的核心身份哈希相同，launcher 可以选择任一兼容的 worker；这不意味着任意不同版本可以混用。

只在新前缀发布新版，保留旧版本目录及其原始字节。开发新版本不会改变旧目录；旧 run 继续用对应旧 worker，旧检查点和 state 仍有效。

## 2. 跨版本继承：新建 run，而非原 run 中途换版本

用户确认的场景：

1. run A 使用 v4 完成 audio。
2. 需要采用新的 annotation 提示词、预算或实现。
3. 新建使用新版的 run B；它具有自己的 GCS state、请求路径和 HF 输出前缀。
4. B 显式继承 A 中兼容、成功的 audio，跳过这些 clip 的 audio 模型调用，再提交自己的 annotation。

此处“新版”指将来改变 annotation 配置的版本。实际 v5 已发布，但只增加外围调度/镜像，核心与 v3/v4 相同，没有实现 audio 导入，也不改变原 run 参数。

A 的 state、代码身份、请求和结果保留原样。B 的来源记录明确说明 audio 来自 A，不能把这些 audio 写成由 B 的新版 worker 重新生成。已经被 Vertex 接收的 annotation 请求不会因后来改代码而改变。

### 有限实现范围

首版若有必要，只支持 **audio → 新 run 的 annotation**。不同时实现任意阶段迁移、自动判断所有历史版本兼容、原 run 热更新参数，或在线 / Batch 间结果互转。

主要工作量在以下边界，而不在文件复制本身：

- **选择可继承集合**：按稳定 clip / request ID 对应到数据 commit、源路径、开始时间和时长；只继承经过契约校验的成功结果。缺失、失败、重复或对应关系不明的行保留为未解决项。
- **证明 audio 兼容**：核对音频输入与预处理、audio 提示词、模型、结果格式和相关实现。完整 code_hash 不同可以是 annotation 改动造成的，但必须解释 audio 为什么仍可复用，不能靠一个“接受差异”开关绕过不兼容。原始 token 设置也要保留；当前 cap 是 run 级参数，不能笼统称为“与 audio 无关”。
- **处理尚未收集的 audio**：当前 tick 收集后会自动提交 annotation。若 A 只完成了 Vertex audio 计算，尚未收集，必须先设计受控的只收集步骤，或让导入工具按正确契约验证原始输出；不能为了拿到 audio 而无意提交 A 的 annotation。
- **保留来源证据**：B 记录 A 的 state URI 与 generation、release / code_hash、每个 clip 的 audio 对象 URI 与内容哈希，以及实际配置差异。共享媒体引用时，要保证 B 完成前源对象仍然存在。
- **避免重复提交**：使用新 prefix；导入与初始化可安全恢复；不能修改 A 的 submission intent，也不能在提交结果不明确时盲目再次创建 Vertex Job。
- **明确运行归属**：B 接手前，确认 A 没有仍会处理同一范围的 worker / schedule。工具应报告冲突，由操作人明确处置；不自动取消 A。

复杂度评估：上述有限导入是中等复杂度，需有恢复和错误路径测试；通用跨版本自动迁移会显著扩大复杂度。目前不估算工期，也不提前建设通用系统。

### 将来实施时的验收

- 对兼容的合成或固定样本创建新 prefix，只提交 annotation，audio 模型调用数为零。
- 旧 state、旧请求、旧结果及旧发布目录逐字节不变。
- 音频输入、时间范围、audio 提示词或契约不兼容时明确拒绝继承。
- 失败 / 缺失行没有被伪装为成功；导入计数能与明确选择的 clip 集合对账。
- 重复执行与中断恢复不会重复导入或重复提交付费请求。
- 测试一律使用新建的独立临时目录与测试前缀，不写默认或正式输出。

## 3. 在线 / Batch 解耦：保护旧版本，单独定义新版身份

当前 `Pipeline.identity()` 对 `castle_pipeline/*.py` 全部文件计算在线指纹；Batch 的 `code_hash()` 也覆盖这些文件，另加 `batch_pipeline.py`。因此即使只改 Batch 专用文件，新代码树计算出的在线指纹也会变化。

**准确的影响范围**：旧在线 run 继续使用旧发布目录时不受影响。问题只出现在使用新代码树运行在线流程、希望复用旧在线检查点时：新指纹不同，旧结果可能不被复用；它们并没有被删除或改坏。

### 会不会造成不兼容

| 对象 | 未来解耦的预期影响 |
|---|---|
| 已发布旧目录、原 tag / manifest | 不修改，仍可复现原身份 |
| 使用旧 worker 的旧 run | 保持原行为，可继续处理 |
| 采用新身份方案的新 release | 指纹预计会改变一次，这是显式版本边界 |
| 新版直接读取旧检查点 | 不承诺自动兼容；默认保留旧 worker 续跑，迁移另行讨论 |
| 新方案建立后的后续版本 | 仅修改 Batch 专用实现时，在线身份应保持不变；反向同理 |

因此不能承诺“所有哈希都不变”。要保证的是旧路径继续可用，以及新版后续不再因无关文件变化而失去复用。

### 保守实施路径

1. **先盘点真实依赖**，区分在线专用、Batch 专用、共享实现。当前 Batch 从 `runner.py` 导入 `atomic_json`、`cleanup_media`、`clip_windows`、`fingerprint` 等函数，不能直接把 `runner.py` 从 Batch 身份集合排除。
2. **先明确身份文件集合**，不把“大规模移动目录”作为前提。如共享工具妨碍隔离，再将必要公共函数迁入明确的共享模块；共享模块变化应影响两边身份。
3. **为新方案命名并使用相对路径键**，例如已有但尚未启用的 `relpath-v1`；禁止把旧方案的 basename 键原地改写。旧 manifest 仍按自己声明的方案验证。
4. **独立测试新版**：先做离线依赖边界测试和旧版本回归；新 release 发布到新目录。首次真实验证限定一个新的小范围，不自动重跑历史数据。
5. **旧 run 继续挂载旧代码**。launcher 按 state 选择相应版本，不统一替换成最新版；不修改旧 state 的哈希以强行通过检查。

本地开发无需等待所有旧 run 结束。需要避免的是覆盖旧发布物、让旧 run 挂载不匹配代码，或让新旧 worker 同时处理同一个 state / 输出范围。回退以选择旧 worker、保留新 run 独立结果为基础，不通过改写 state 伪装兼容。

### 将来实施时的验收

- 在新方案下，改 Batch 专用文件只改变 Batch 身份；改在线专用文件只改变在线身份；改实际共享依赖改变两者身份。
- 共享依赖不遗漏，新增文件不会因 basename 冲突被静默吞掉。
- 从原 tag / 发布快照重算的旧哈希与原 manifest 一致；用旧 worker 复用旧检查点仍通过。
- 用不兼容的新版 worker 处理旧 state 时，明确拒绝，且不提交模型任务。
- 不把旧检查点的自动迁移作为本项验收要求；也不以绕过哈希检查来获得兼容。

## 4. 内容哈希核验：只读报告

范围限定为：读取本地受版本控制的 manifest，下载对应发布目录中的文件到独立临时目录，对照原始字节 SHA-256，输出核验结果。

报告应包含 release、核验时间、核验文件数、缺失文件、内容不同的文件及 expected / actual 哈希。覆盖 `identity_files`、`auxiliary_files`、`prompt_files`；核心 code_hash 按 manifest 指定的方案重算。文件名相同不能替代内容核验，行尾也属于被核验的字节。

核验失败只产生报告和明确的退出状态，不自动补传、覆盖、删除或修复发布目录，不重写 manifest，不取消或修改正在执行的任务。worker 启动校验、强制发布闸门、权限 / 存储侧锁定等均为独立议题，本轮不扩展。

已有工具：`_bench/verify_release_bytes.py --release <release>` 能对当前 basename-v1 发布物做独立字节回读。它尚未整合进正式发布路径，尚不能作为未来 relpath-v1 的通用验证器；扩展时应先补对方案的正确分派。`release.py publish --verify-only` 当前只做本地检查并跳过网络，不能把它的通过当作云端内容已核验。

以后整理正式命令时，先保留上述只读边界；测试用正确文件、缺失文件、同名但内容不同的文件、LF/CRLF 差异及下载失败验证报告。此项成本较低，不必连带实施其它版本重构。

## 5. 恢复讨论时先确认什么

开始任一实现前，重读本文件和相关代码，核对当时的 release、实际依赖及用户需要；不要直接执行早期文档的全部待办，也不要把本次讨论当作发布或模型调用授权。若没有新的需求，继续使用“一条 run 固定版本，新任务选择合适的新 release”的现有流程。
